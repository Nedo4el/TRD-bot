# POC-скринер

Находит POC-уровни (Point of Control — цена с максимальным накопленным
объёмом) за 8 исторических окон, хранит их в SQLite и отдаёт сигнал в
дашборд, когда цена входит в 10 % зону ближайшего кластера уровней.

**Ключевой принцип:** уровень существует независимо от того, касалась ли его
цена. Касание — триггер для сигнала, а не условие существования уровня.
Подтверждение (`confirmed`) определяется объёмом, а не числом касаний.

## Структура

```
bot_screener_yrovni/poc_scanner/
├── config.py     # POCConfig, окна, PER_SYMBOL_OVERRIDES, чтение .env
├── profile.py    # Volume Profile: POC, Value Area (VAH/VAL)
├── clusters.py   # кластеры 5 %, ближайший кластер, зона 10 %
├── store.py      # SQLite: poc_levels, zone_state, poc_signals_log, klines
├── klines.py     # Bybit v5 /market/kline + кэш + лимит 10 req/s
├── scanner.py    # POCScanner: расчёт, слияние, сигналы
├── signals.py    # POCSignal (JSON роботу)
├── timeutil.py   # ISO-время UTC
├── main.py       # цикл по закрытию 5m свечи, POST /api/signal
└── .env.example  # все параметры
```

## Запуск

Из корня проекта:

```powershell
# один проход по одному символу (проверка)
.venv\Scripts\python.exe -m bot_screener_yrovni.poc_scanner.main SOLUSDT --once

# постоянный цикл по списку
.venv\Scripts\python.exe -m bot_screener_yrovni.poc_scanner.main SOLUSDT ETHUSDT

# или список из POC_SYMBOLS в .env
.venv\Scripts\python.exe -m bot_screener_yrovni.poc_scanner.main
```

Первый запуск скачивает историю (для 730d на 4h — 4380 свечей, 5 запросов),
дальше каждые 5 минут добирается только хвост из кэша.

### Дашборд: весь рынок

Кнопка «Сканировать» у карточки «Уровни POC» сканирует не только
`POC_SYMBOLS`, а весь рынок по настройкам панели «Все монеты»: минимальный
оборот за 24 ч, исключённые символы, минимальное |Δ24ч| и число монет.
`POC_SYMBOLS` добавляются к списку всегда (удобно держать вручную отобранные
пары). ТФ панели на POC не влияет: цена сравнения — своя закрытая 5m свеча
(`PRICE_INTERVAL`).

нормально, сигнал всё равно записан в БД и JSONL.

## Модель «ближайший кластер»

С 22.11.2026 сигнал считается по кластерам, а не по отдельным уровням:

1. Уровни, отстоящие друг от друга по формуле `|A-B| / min(A,B) < 5 %`
   (`CLUSTER_MERGE_PCT`), объединяются в кластер **транзитивно**: если
   A~B и B~C, все три в одном кластере.
2. Торговый уровень кластера — среднее арифметическое цен участников,
   округлённое до 0.1 % (4 значащие цифры).
3. Мониторится только **ближайший к цене** кластер. Цена входит в зону
   10 % (`ZONE_PCT`, расстояние `|цена − уровень| / цена`) — сигнал.
   Остальные кластеры игнорируются.
4. Сигнал один раз за вход в зону: пока цена не вышла из зоны и не
   вернулась, повтора нет. Состояние зоны (`in_zone`, `episode`) хранится
   в таблице `zone_state` и переживает рестарт.
5. Сильный сигнал — только подход после паузы: до входа цена не была в зоне
   уровня `ZONE_QUIET_HOURS` часов (24), а сам вход случился не раньше
   `ZONE_FRESH_HOURS` часов (2) назад. Если цена «сидит» у уровня дольше —
   это не сигнал, в лог пишется пояснение. Пауза и время в зоне считаются
   по закрытым свечам цены (5m), поэтому фильтр работает и после сброса
   состояния.
6. Уровень участвует в сигналах, только если цена **уходила от него** хотя
   бы на `MIN_DEPARTURE_PCT` (20 %) внутри его собственного окна: от начала
   отрезка/окна до текущего момента, по закрытиям 1h (или 4h для старых
   уровней). POC свежего 7d/14d-окна у текущей цены так не отличить от
   зоны торговли — он отбрасывается. Отброшенные уровни пишутся в лог
   одной строкой (`уровни без ухода цены на 20% — пропуск: ...`).
7. В сигнале: `symbol`, `direction` (`long` — цена сверху, `short` — снизу),
   `entry_price` (уровень кластера), `ts`, `signal_id`. TP и SL считает
   робот — скринер их не передаёт.
8. Цена для сравнения — закрытая **5m** свеча (`PRICE_INTERVAL`); POC
   по-прежнему считается по 1h/4h.

Сигнал уходит на `POST /api/signal` дашборда (идемпотентность по
`signal_id`: повторная отправка не создаёт дубль). Дашборд показывает его
на вкладке «POC-сигналы»: при `AUTO_TRADE=false` — «ожидает подтверждения»,
после кнопки «Подтвердить» или при `AUTO_TRADE=true` — «в работе». Флаг
переключается тумблером в дашборде без перезапуска сервера.

Пример лога:

```
СИГНАЛ AKEUSDT long entry=0.005219 (цена 0.005259, 0.76%) кластер из 1 уровней: 2026-11,30d
```

Чистка после смены окон:

```powershell
.venv\Scripts\python.exe -m bot_screener_yrovni.poc_scanner.main SOLUSDT --prune
```

`--prune` удаляет rolling-уровни, чьи окна больше не входят в `POC_WINDOWS`
(уровни исторических отрезков не трогает).

## Исторические отрезки (старые уровни)

Скользящие окна видят только «последние N дней», поэтому старые объёмные
уровни выпадают: у SOXSUSDT сентябрьский POC 33.27 не попадал ни в одно окно
(30d начинался 23.10, а 180d отбрасывался из-за нехватки истории). Второй
источник — POC по фиксированным отрезкам истории:

```
SEGMENT_MODE=calendar_month   # calendar_month | fixed_30d | off
TOP_N_SEGMENTS=12             # сколько последних отрезков хранить
SEGMENT_MIN_VOLUME_USD=10000000
```

- `calendar_month` — каждый календарный месяц считается отдельно (свечи 4h),
  `segment_start_ts`/`segment_end_ts` — его первая и последняя свеча;
- `fixed_30d` — блоки по 30 дней назад от последней свечи;
- `off` — только rolling-окна (поведение до появления отрезков).

Возраст такого уровня — сколько дней прошло с `segment_end_ts`
(в логе: `calendar_month POC 2026-09: price=33.26575, vol=$236.1M, age=52d`).
`MIN_POC_AGE_DAYS` применяется и к ним: текущий месяц всегда моложе порога,
поэтому в сигналах участвуют только завершённые месяцы.

Слияние: если POC отрезка попадает в `MERGE_POC_PCT` к существующему
rolling-уровню, отрезок добавляется в него (`source_windows` += `2026-09`,
тип остаётся `rolling`, возраст — максимум, объём суммируется). Иначе
создаётся отдельный уровень с `segment_type='calendar_month'`.

Пример старта на SOXSUSDT (128 дней истории):

```
POC levels loaded: 7d=ok(age=7), 14d=ok(age=14), 30d=ok(age=30,partial),
  180d=ok(age=128,partial), 365d=ok(age=128,partial), 730d=ok(age=128,partial)
POC segments loaded: 2026-07 (vol=$125.1M), 2026-08 (vol=$199.5M),
  2026-09 (vol=$236.1M), 2026-10 (vol=$683.3M), 2026-11 (vol=$1348.4M)
calendar_month POC 2026-09: price=33.26575, vol=$236.1M, age=52d WALL
merged calendar 2026-10 POC 45.28665 into rolling level (age updated to 128d)
```

## Смена окон

Окна задаются в `.env` (или `poc_scanner/.env`) одной строкой:

```
POC_WINDOWS=3d,5d,7d,14d,30d,180d,365d,730d
```

- формат `<дни>d`, порядок сохраняется;
- до 30 дней — часовые свечи, длиннее — четырёхчасовые;
- после смены окна старые уровни в БД остаются: удалить их можно командой
  `... main SOLUSDT --prune` (убирает rolling-уровни, чьи окна больше не
  входят в `POC_WINDOWS`) или вручную
  (`DELETE FROM poc_levels WHERE symbol='SOLUSDT'`), иначе новые POC
  сливаются со старыми в пределах `MERGE_POC_PCT`.

## Параметры

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `POC_WINDOWS` | `3d,5d,7d,14d,30d,180d,365d,730d` | окна расчёта |
| `POC_BINS` | 100 | корзин в профиле |
| `VA_PERCENT` | 0.68 | доля объёма в Value Area |
| `CONFIRM_VOLUME_THRESHOLD` | 50 000 000 | объём, подтверждающий уровень |
| `MIN_SIGNAL_VOLUME` | 10 000 000 | минимум объёма для сигнала |
| `WALL_VOLUME_THRESHOLD` | 200 000 000 | порог «стены» |
| `TOUCH_PROXIMITY_PCT` | 0.005 | не используется моделью кластеров |
| `MERGE_POC_PCT` | 0.01 | слияние уровней в БД до кластеризации (1 %) |
| `CLUSTER_MERGE_PCT` | 0.05 | слияние уровней в кластер (5 %) |
| `ZONE_PCT` | 0.10 | зона сигнала от цены до уровня (10 %) |
| `ZONE_QUIET_HOURS` | 24 | сколько часов цена не должна подходить к уровню до сигнала |
| `ZONE_FRESH_HOURS` | 2 | насколько свежим должен быть вход в зону (часы) |
| `MIN_DEPARTURE_PCT` | 0.20 | минимальный уход цены от уровня внутри его окна (20 %), иначе уровень не даёт сигналов |
| `PRICE_INTERVAL` | `5` | интервал цены сравнения (закрытая свеча) |
| `MIN_CONFIDENCE` | 0.6 | не используется моделью кластеров |
| `MIN_POC_AGE_DAYS` | 7 | возраст уровня (длина окна): короче — окно не считается |
| `MAX_POC_AGE_DAYS` | 730 | старше — игнорировать |
| `POC_HISTORY_DB` | `data/poc_history.sqlite` | БД уровней и кэша свечей |
| `HISTORY_CACHE_DAYS` | 730 | глубина истории |
| `SIGNAL_ENDPOINT` | `http://127.0.0.1:8787/api/signal` | куда POST-ить сигнал |
| `TOUCH_COOLDOWN_SEC` | 3600 | не используется моделью кластеров |
| `SIGNAL_COOLDOWN_SEC` | 3600 | не используется моделью кластеров |
| `ATR_PERIOD` | 14 | не используется моделью кластеров |
| `SEGMENT_MODE` | `calendar_month` | POC по отрезкам: `calendar_month` / `fixed_30d` / `off` |
| `TOP_N_SEGMENTS` | 12 | сколько последних отрезков хранить |
| `SEGMENT_MIN_VOLUME_USD` | 10 000 000 | мин. объём отрезка для уровня |

Переопределения по символу (`PER_SYMBOL_OVERRIDES` в `config.py`):
`BTCUSDT` — $500M, `SOLUSDT` — $100M, `AVAXUSDT` — $30M.

## Схема БД

`poc_levels` — уровни (одна строка на уровень, уникальность `symbol` +
`poc_price`); `source_windows` — JSON-список окон и отрезков
(`["30d", "2026-09"]`), `window_volumes` — JSON `{окно: объём}`;
`poc_age_days` — возраст уровня (максимум по его окнам для `rolling`,
давность `segment_end_ts` для `calendar_month`), `first_created_ts` — начало
самого старого окна (справочно, в фильтре не участвует),
`last_calculated_ts` обновляется каждым сканом; `segment_type`
(`rolling` / `calendar_month` / `fixed_30d`), `segment_start_ts`,
`segment_end_ts`, `partial_window` (истории не хватило на окно/месяц);
`touch_count`/`last_touch_ts` — касания.

`poc_signals_log` — каждый выданный сигнал (`raw_json` — полное тело).

`klines` — кэш свечей (`PRIMARY KEY (symbol, interval, open_time)`).

`zone_state` — состояние зоны ближайшего кластера: `in_zone`, `episode`,
`direction`, `level_price`, `updated_ts` (одна строка на символ).

Версия схемы — `PRAGMA user_version`; `migrate()` создаёт таблицы на пустой
БД и добавляет новые колонки к уже существующей.

## Отличия от исходного ТЗ (осознанные)

1. **Объём уровня не копится.** В ТЗ `total_volume_at_level += новый объём`,
   но при пересчёте каждые 5 минут это раздуло бы объём до бесконечности и
   все уровни стали бы «стенами». Хранится `{окно: объём}`, повторный расчёт
   того же окна **заменяет** значение, объёмы разных окон суммируются.
2. **Сигнал — по кластеру, без confidence и `action`.** Модель от 22.11.2026
   заменила зону ±0.5 % и порог confidence: сигнал выдаётся по входу в
   10 % зону ближайшего кластера, TP/SL считает робот. Поля
   `TOUCH_PROXIMITY_PCT`, `MIN_CONFIDENCE`, кулдауны и `ATR_PERIOD`
   оставлены в конфиге для совместимости, но на сигналы не влияют.
3. **Анти-спам — эпизодом зоны, а не кулдауном.** Один сигнал на
   кластер+направление до выхода цены из зоны; состояние в `zone_state`
   переживает рестарт.
4. **Свечи грузятся через stdlib `urllib`,** а не `ccxt`: ccxt в проекте нет,
   а Bybit v5 REST достаточно. pandas/numpy — уже в `requirements.txt`.
5. **Возраст уровня — длина окна, а не дата записи в БД.** Иначе на новом
   символе все уровни «моложе суток» и `MIN_POC_AGE_DAYS` отбрасывал бы их
   все: бот был бы слепым первые 7 дней. Окна короче `MIN_POC_AGE_DAYS`
   (`3d`, `5d` при дефолте 7) не считаются вовсе; возраст слитого уровня —
   максимум по его окнам. `first_created_ts` хранит начало самого старого
   окна и нужен только для отчётности.
6. **Нехватка истории не отбрасывает окно.** Окно считается по фактическим
   свечам с `partial_window=1`, а возраст — реальный охват (у SOXSUSDT
   180d/365d/730d дают возраст 128 дней). Окна с одинаковым фактическим
   охватом больше не считаются дважды — остаётся самое длинное. Перекрытие
   окон разной длины (например, полный 365d и partial 730d) по-прежнему
   суммирует оборот, поэтому объём такого уровня — верхняя оценка.
7. **Текущий календарный месяц в сигналах не участвует.** Его
   `segment_end_ts` — последняя свеча, возраст ~0, и фильтр
   `MIN_POC_AGE_DAYS` его отбрасывает; уровень всё равно пишется в БД.
